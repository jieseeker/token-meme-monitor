# 后端优化方案第一版

整体看，当前后端结构是清晰的：

`Alpha watchlist -> DexScreener pair seed -> snapshot 清洗 -> feature -> signal -> alert/outcome`

主要问题不在“代码跑不起来”，而在生产运行中可能出现：

- 数据失真
- 重复重刷
- 误告警
- API 负载偏高
- 后验 outcome 被污染
- 候选指标窗口不准

本方案优先修确定性 bug 和 worker 调度问题，策略含义变化放到后面，避免把系统稳定性修复和评分策略调整混在一起。

## 1. 高优先级确定性问题

### 1.1 outcome 重复回填

位置：

- `token_meme_monitor/database.py:list_signals_ready_for_outcomes`

当前查询条件类似：

```sql
o.signal_id IS NULL
OR s.observed_at > now - 24h
```

问题：

- 2h 以上、24h 以内的 signal 会在每个 worker cycle 里被反复选中
- `backfill_outcomes()` 当前每轮都跑，signal 增多后会明显拖慢 worker
- 重复评估也会让 outcome 表频繁写入，增加 SQLite 压力

建议：

- 按阶段回填：
  - 未评估过的 signal，达到 2h 后先评估 2h outcome
  - 达到 24h 后再评估 24h outcome
- 或者基于 `outcomes.evaluated_at`、`sample_count_2h`、`sample_count_24h` 判断是否还需要重评
- 给每轮 outcome backfill 加 batch limit
- 后续可以把 outcome backfill 从主 refresh cycle 拆成低频任务

### 1.2 seed pair 强制复活已归档 pair

位置：

- `token_meme_monitor/database.py:upsert_seed_pair`

当前 `ON CONFLICT(pair_address)` 会强制：

```sql
state = 'watching',
active = 1,
next_refresh_at = excluded.next_refresh_at
```

问题：

- 已经 `archived` 的 pair 可能被下一轮 Alpha seed 复活
- 异常 pair 也可能被重复拉回 due 队列
- 结合“每轮全量 seed Alpha”，会导致反复重刷

建议：

- 新 pair 插入时设为 `watching/active=1`
- 已存在 pair 更新时只刷新 metadata、token symbol/name、quote 信息
- 不要无条件覆盖 `state/active/next_refresh_at`
- 如确实需要重新激活，必须有明确条件，例如：
  - token 仍在 Alpha 列表
  - 上次归档原因不是严重风险
  - 距离上次归档超过指定冷却期

### 1.3 severe risk 仍可能触发告警

位置：

- `token_meme_monitor/signals.py:SignalEngine.evaluate`

当前严重风险包括：

- `missing_price`
- `liquidity_near_zero`
- 非 Alpha 模式下的 `stale_pair`

问题：

- `pair_state` 会因为 `liquidity_near_zero` 变成 `archived`
- 但 `should_alert` 只排除了 `missing_price` 和非 Alpha 下的 `stale_pair`
- 如果低流动性币因为成交、买盘、放量等分数叠高，可能出现 `pair_state=archived` 但 `should_alert=True`

建议：

- `should_alert` 统一排除所有 severe flags
- 或者更直接要求 `pair_state == "alerted"` 才允许告警

### 1.4 `pair_created_at` 缺失时会无限 due

位置：

- `token_meme_monitor/orchestrator.py:_refresh_pair`

问题：

- 如果 `pair_created_at` 解析失败，当前逻辑只 `return`
- pair 没有被 schedule retry，也没有归档/禁用
- 下一轮仍然 due，形成无意义循环

建议：

- 对缺失 `pair_created_at` 的 pair 调用 `schedule_pair_retry`
- 如果连续失败次数过多，标记 inactive 或 archived
- metadata 里记录 `last_retry_reason=missing_pair_created_at`

## 2. Worker 调度与 API 负载

### 2.1 Alpha seed 每轮全量请求 DexScreener

位置：

- `token_meme_monitor/orchestrator.py:_sync_alpha_watchlist`

问题：

- `binance_alpha_refresh_minutes` 只控制 Alpha token list cache
- 即使命中 Alpha cache，仍会对所有 token 分批请求 DexScreener
- 默认 15 秒一轮时，DexScreener 压力会很高

建议：

- 拆成两个独立节奏：
  - Alpha token list refresh：按 `binance_alpha_refresh_minutes`
  - Alpha pair seed refresh：更长 TTL，例如 10-30 分钟
- pair seed 只处理：
  - 新出现的 Alpha token
  - 数据库里还没有 pair 的 token
  - 上次 seed 失败且超过 retry interval 的 token
- 记录 token 级别 seed 状态，例如：
  - `pair_seeded_at`
  - `pair_seed_failed_at`
  - `pair_seed_failure_reason`

### 2.2 due pair 的 Alpha 过滤应下沉到 SQL

位置：

- `token_meme_monitor/database.py:list_due_pairs`
- `token_meme_monitor/orchestrator.py:run_cycle`

当前逻辑：

1. SQL 先从所有 active pair 里取 `LIMIT`
2. Python 再过滤 `token_address in alpha_token_map`

问题：

- 如果库里有旧的非 Alpha active pair，可能挤占 limit
- 真正到期的 Alpha pair 可能刷不到

建议：

- 仓储层新增 `list_due_pairs_for_tokens(token_addresses, limit)`
- 在 SQL 里完成 Alpha token 过滤
- 或者在 Alpha 模式切换时，把非 Alpha active pair 显式 inactive/archive

### 2.3 due pair 排序可能造成 watching/new 饥饿

位置：

- `token_meme_monitor/database.py:list_due_pairs`

当前排序优先级：

1. `alerted`
2. `focused`
3. `watching`
4. `new`

问题：

- focused/alerted 多时，watching/new 可能长期得不到刷新
- 新 Alpha token 可能延迟进入有效监控

建议：

- 增加 per-state quota
- 或按 overdue 时间混排
- 或保留高优先级队列，同时给 watching/new 固定比例名额

## 3. 数据质量与策略风险

### 3.1 Alpha 官方值无条件覆盖实时值

位置：

- `token_meme_monitor/market_data.py:sanitize_pair_snapshot`

当前 Alpha 模式下，`price_usd / market_cap / fdv` 优先使用 Alpha reference。

问题：

- Alpha 官方值如果滞后，会削弱短周期信号
- `h1_return_live / h4_return_live / h24_return_live` 会被钝化
- outcome 的 entry price 也可能偏离真实交易时价格

建议：

- 正常情况下保留 DexScreener 实时值
- 只有 DexScreener 缺失、非法、或与 Alpha reference 偏离超过阈值时才 fallback
- 同时保留 `_data_quality.sources`，方便后续分析字段来源
- 如果仍要优先 Alpha reference，需要在策略文档里明确这是“稳定性优先，不追求最实时价格”

### 3.2 DexScreener pair snapshot 返回缺少校验

位置：

- `token_meme_monitor/clients/dexscreener.py:fetch_pair_snapshot`

问题：

- 当前默认取 `pairs[0]`
- 未验证返回的 `pairAddress/baseToken/quoteToken` 是否匹配请求
- 第三方接口异常、重定向、或返回结构变化时，可能写错 token 的快照

建议：

- 校验 `pairAddress == requested pair_address`
- 校验 base/quote token 与请求 token 匹配
- 校验 chainId 与配置一致
- 不匹配时返回 `None` 或抛出可重试异常，并记录 reason

### 3.3 best pair 只接受 Alpha token 作为 baseToken

位置：

- `token_meme_monitor/clients/dexscreener.py:fetch_best_pairs_for_tokens`

问题：

- 当前只把 Alpha token 是 `baseToken` 的 pair 纳入候选
- 如果某些池子里 Alpha token 在 quote side，会 seed 不到

建议：

- 如果这是有意策略，在文档里写明
- 如果不是，应支持 Alpha token 出现在 base 或 quote 两侧
- 但需要谨慎处理价格、买卖方向、quote symbol，避免方向反转造成指标误读

### 3.4 outcome horizon 覆盖不足

位置：

- `token_meme_monitor/outcomes.py:evaluate_outcomes_for_signal`

问题：

- 当前 2h/24h outcome 取 `<= end_2h/end_24h` 的最后一个 snapshot
- 不要求最后一个 snapshot 接近 horizon
- 如果 24h 内最后一次数据其实在 3h，可能被当成 24h return

建议：

- 给 horizon 设置最小覆盖时间
  - 例如 2h outcome 至少覆盖到 90 分钟以后
  - 24h outcome 至少覆盖到 20 小时以后
- 或设置 horizon 容忍窗口
  - 例如取 `[horizon - tolerance, horizon + tolerance]` 内最近点
- 覆盖不足时，`horizon_*_return` 先记为 `None`
- `max_return_*` 可以保留为窗口内最大收益，但要单独解释 sample coverage

### 3.5 候选指标窗口不准

位置：

- `token_meme_monitor/indicator_candidates.py`

问题：

- 当前先按小时 collapse，再计算 `h1_return_live / h4_return_live / h24_return_live`
- 如果当前时间不是整点，小时 collapse 后的点可能让实际 lookback 偏离
- 候选指标目前不参与评分，影响有限；但接入评分前需要修正

建议：

- 收益率指标直接从原始 snapshots 中取 `<= cutoff` 的最近一条
- volume impulse 可以继续按小时聚合，但要明确“每小时取最后一条”的语义
- 增加单测覆盖非整点时间，例如 `12:45` 计算 1h lookback 时应尽量取 `11:45` 前后的合理点

## 4. 性能与稳定性优化

### 4.1 holder/top10 查询不应阻塞主刷新链路

位置：

- `token_meme_monitor/orchestrator.py:_refresh_pair`

问题：

- holder count 和 top10 holder share 在 pair refresh path 内同步请求
- focused pair 多时，会拖慢整个 worker cycle
- 外部 API 抖动会影响主行情刷新

建议：

- 拆成低频 side job
- 或建立限流队列
- 或每轮只刷新少量 holder metrics
- holder 类指标接入评分前，先记录但不影响告警

### 4.2 outcome backfill 不应每轮无边界执行

位置：

- `token_meme_monitor/orchestrator.py:run_cycle`

问题：

- 每个 worker cycle 都调用 `backfill_outcomes()`
- 随 signal 增多，查询和回填会越来越重

建议：

- 固定间隔执行，例如每 5-15 分钟
- 每轮限制最大处理数量
- 补充索引以支持 ready outcome 查询

### 4.3 token metadata 合并在多 worker 下可能丢字段

位置：

- `token_meme_monitor/database.py:upsert_token`

问题：

- 当前是读 metadata -> Python merge -> 写回
- 单 worker 下问题不大
- 多进程 worker 时可能发生字段覆盖

建议：

- 当前阶段明确只支持单 worker 写库
- 如果要多 worker，需要事务保护或数据库侧 JSON patch

### 4.4 BSC block timestamp cache 没有上限

位置：

- `token_meme_monitor/clients/bsc.py`

问题：

- 长时间运行会持续增长
- 单个 datetime 不大，但没有上限不利于长期进程

建议：

- 简单 LRU
- 或只缓存当前扫描窗口附近的 block timestamp

## 5. 建议实施顺序

### 第一阶段：先修确定性 bug

目标：避免误告警、重复回填、状态反复复活。

任务：

1. 修 `should_alert`，统一排除 severe flags
2. 修 `upsert_seed_pair`，避免强制重置已有 pair 状态
3. 修 outcome ready 查询，避免 2h-24h 信号每轮重复回填
4. 修 `pair_created_at` 缺失时无限 due

### 第二阶段：降低 API 压力和刷新饥饿

目标：让 worker 更稳定，避免外部 API 负载过高。

任务：

1. Alpha token refresh 与 pair seed refresh 分离
2. pair seed 改成 TTL/增量策略
3. due pair 的 Alpha 过滤下沉到 SQL
4. due pair 增加 per-state quota 或 overdue 混排

### 第三阶段：加强数据质量边界

目标：避免第三方异常数据写错库，避免后验结果失真。

任务：

1. DexScreener snapshot 增加 pair/base/quote/chain 校验
2. outcome horizon 增加覆盖时间要求
3. 重新评估 Alpha reference 覆盖策略
4. 修候选指标 lookback 窗口

### 第四阶段：拆分低频任务

目标：减少主行情刷新链路阻塞。

任务：

1. holder/top10 拆成 side job 或限流任务
2. outcome backfill 改为低频批处理
3. 多 worker 前补事务/锁/JSON patch 策略
4. BSC timestamp cache 加上限

---

## 6. 当前不建议马上做的事

- 不建议立刻把候选指标接入正式评分
- 不建议同时大改评分阈值和清洗策略
- 不建议在 worker 还会重复 seed、重复 backfill 时扩大发送告警范围
- 不建议在 SQLite 单 worker 语义未明确前引入多 worker 写库

先把采集、状态、告警、outcome 的基础行为修稳，再做策略层面的加权和分桶优化。
